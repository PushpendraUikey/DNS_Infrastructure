# Phase 7 — Encrypting the Last Mile (DoT / DoH)

Phase 6 showed the resolver→client hop is unauthenticated. This phase encrypts and
authenticates it: a private CA issues the resolver a certificate for the DNS name
`resolver.cs6008.local`, the client installs the CA and reaches the resolver **by name**
over DoH (443) / DoT (853), validating the certificate. The last-mile attack is then
mounted three ways against two kinds of client, and only one combination lands.

## What's new vs Phase 6

- **`make-certs.sh`** — stands up a private CA and issues: the resolver cert
  (SAN `DNS:resolver.cs6008.local`, **no IP SAN**) and a **rogue** self-signed cert with
  the same name (for attempt ii). Keys are generated, never committed.
- **Resolver speaks encrypted DNS** (`resolver/named.conf`): `tls` + `http` blocks, with
  `listen-on` for Do53 (53), DoT (853) and DoH (443/`/dns-query`). Upstream DNSSEC
  validation is unchanged.
- **Client trusts the CA, reaches by name** (`compose.yml`): `ca.crt` is installed into the
  client's trust store in `entrypoint.sh` (no `-k`), and `extra_hosts` maps
  `resolver.cs6008.local` → `172.16.2.10` (a dummy IPv6 entry + `curl -4` avoids any
  cleartext bootstrap lookup).
- **`scripts/block443.sh` / `unblock443.sh`** — iptables rules on edge-router that drop
  DoH/DoT to the resolver (attempt iii).
- **`attacker/rogue_server.py`** — a TLS server presenting the rogue cert on 443 (attempt ii).
- The interceptor is the Phase 6 Do53 forger, now also recomputing TCP checksums so it can
  faithfully relay the encrypted stream it cannot read.

## Setup

```sh
./make-certs.sh                       # private CA + resolver cert + rogue cert (into pki/)
./sign.sh                             # signed zones + trust anchor (as in Phase 3)
docker compose up --build -d
```

## Verify

```sh
./run.sh verify
# DoH resolution (strict client): safe (real page)
```

The client resolves `example.com` over DoH with the certificate validating cleanly against
the CA, upstream DNSSEC still holds, and a capture on edge-router shows **no cleartext DNS**
for the lookup (all client↔resolver traffic is TCP 443).

## Attack — three attempts × two clients

Two client behaviours are exercised from the one `client` container:
- **strict** — DoH only, never falls back to cleartext.
- **permissive** — probes the encrypted transport; if it is *denied* it opportunistically
  falls back to cleartext, but a *bad certificate* is a hard failure (no fallback).

```sh
./run.sh i      # (i)   alter the answer in transit  (Do53 forge running; client speaks DoH)
./run.sh ii     # (ii)  impersonate the resolver with a rogue certificate
./run.sh iii    # (iii) deny the encrypted transport (block 443/853) to force fallback
```

Expected results:

| Attempt | strict client | permissive client |
|---------|---------------|-------------------|
| (i) alter in transit | safe | safe |
| (ii) rogue certificate | safe (cert rejected) | safe (cert rejected) |
| (iii) deny transport | safe (fails closed) | **LANDED** (downgrades to cleartext, forged) |

- **(i)** The answer is inside TLS; the on-path forger can relay but not read or alter it,
  so both clients get the real page.
- **(ii)** The rogue cert isn't signed by the CA, so certificate validation fails before any
  answer is exchanged — both clients refuse, even though the name matches.
- **(iii)** Blocking 443/853 is the only thing that works, and only against the client that
  permits a cleartext fallback: it drops to Do53, where the forger hijacks it. The strict
  client fails closed.

## Reset / teardown

```sh
./run.sh reset
docker compose down
```

## Notes

- **Which combination lands and why:** only (iii) × permissive. Encryption + authentication
  defeat in-transit tampering (i) and impersonation (ii) outright; the residual risk is a
  **downgrade**, and it only succeeds if the client is willing to speak cleartext.
- **DoT vs DoH:** we enable both and drive the client over DoH. DoH (443) blends with HTTPS
  and is hard to block selectively; DoT (853) is a dedicated port, easier for a network to
  identify and block (which is exactly what makes attempt iii's block cleaner to reason
  about). State your choice and this trade-off.
- **What an encrypted, authenticated last mile still does not protect:** availability (it can
  be blocked, forcing fallback or denial), metadata/traffic analysis (an observer still sees
  that you talked to the resolver and how much), and anything upstream of the resolver — the
  resolver→authoritative hops are still plain, protected only by DNSSEC.
- **PKI keys:** no private key is committed — `pki/` is regenerated by `make-certs.sh`. Make
  sure `pki/` is git-ignored (see the repo `.gitignore`).
